# HWPX(한글) 원고

## 한글 원고 교정: 빨간펜 교정본

한글 원고는 한글 변경 추적 대신 **빨간펜 교정본**으로 돌려준다. 기본 글자 모양(색·취소선·밑줄)만 쓰므로 맥·윈도우 한글에서 같은 파일을 연다.

```bash
python scripts/hwpx_tool.py text 원고.hwpx            # 번호 붙은 문단(편집 목록의 para 번호)
python scripts/hwpx_tool.py redpen 원고.hwpx edits.json [-o 원고_redpen.hwpx] [--report 보고서.md] [--clean 원고_clean.hwpx]
```

편집 목록(JSON):

```json
{"genre": "웹소설", "dialogue": "auto", "terms": ["확정 이름·용어"], "protected_text": ["글자 그대로 지킬 문구"], "edits": [
  {"find": "무리라는건 알고있었다", "old": "무리라는건 알고있었다", "new": "무리라는 건 알고 있었다", "rule": "띄어쓰기", "tier": "확실", "reason": "의존 명사 '건', 보조 용언 '있다'는 띄어 씀"},
  {"para": 159, "old": "아무말도하지", "new": "아무 말도 하지", "rule": "띄어쓰기", "tier": "확실", "reason": "…"},
  {"para": 12, "new_text": "문단 전체를 새로 쓴 글", "rule": "어색한 말", "tier": "권장", "reason": "…"},
  {"para": 20, "after": "기준 문구", "text": "넣을 글", "rule": "…", "tier": "권장", "reason": "…"}
]}
```

- `para`는 `text` 명령의 문단 번호(빈 문단·표 안 문단 포함). `find`는 그 문구가 든 문단이 딱 하나여야 한다. 같은 문단에 여러 편집을 걸 수 있고, 차례대로 적용된다. 같은 문구가 문단에 여러 번 있으면 `occurrence`로 몇 번째인지 준다.
- `terms`와 `protected_text`는 선택이다. 스타일 시트에서 확정한 이름·용어와 사용자가 글자 그대로 지키라고 한 문구만 넣으며, 위험 수정 게이트도 이 목록을 사용한다.
- 결과: `_redpen.hwpx`(빨간 취소선 = 지운 글자, 파란 밑줄 = 넣은 글자), `_편집보고서.md`(편집마다 번호·문단·전후 문맥·규칙·이유). 수정 반영본은 늘 만들어 검증에 쓰되, `--clean`을 줄 때만 파일로 남긴다. 작가가 받을 수정 번호를 알려 주면 그 수정만 넣은 편집 목록으로 `--clean`을 만든다.
- 띄어쓰기·문장부호만 바뀐 곳은 빈칸에 색을 입혀도 보이지 않으므로 어절 전체를 '옛 어절(빨간 취소선) + 새 어절(파란 밑줄)'로 보인다(`무리라는건`→`무리라는 건`). 글자가 바뀐 곳은 바뀐 글자만 표시한다. 수정 반영본은 최소 수정 그대로다.
- 원래 글자 모양을 복제해 색과 선만 바꾼 새 글자 모양 두 개를 머리 정보에 더한다(수정본에는 더하지 않는다).
- 고친 문단의 줄 배치 캐시(`linesegarray`)는 지워 한글이 다시 계산하게 한다. 고치지 않은 문단은 원본과 바이트까지 같다.
- 자동 검증: ZIP 구조, XML 파트, 문단 수, 고치지 않은 문단 동일, 글자 모양 수·참조, 빨간 부분 = 지운 글자·파란 부분 = 넣은 글자, 색이 붙은 조각마다 눈에 보이는 글자가 있음, 수정본 본문 = 기대값. 하나라도 FAIL이면 전달하지 않는다.
- **엔진의 안전장치:** `redpen`은 수정마다 앞뒤 문단과 함께 뜻이 바뀌었는지 판정한다. 사실 항목(강제 되돌림)·확인 항목(기본 적용)과 `decision`·`decision_reason`·`override`는 Word 설명서와 같다: 사실 항목은 `override`와 근거가 없으면 빨간펜에 쓰지 않고, 확인 항목은 `"decision": "REVERT"`일 때만 빼며, 판정은 모두 보고서의 판정 표에 남긴다. 편집 목록 맨 위의 `"genre"`·`"dialogue"`·`"terms"`·`"protected_text"`를 따른다(Word 설명서와 같다). 만든 빨간펜 파일을 대조에 넣을 때는 `hwpx_tool.py text 교정본_redpen.hwpx --redpen final --plain`(원문은 `--redpen original`).
- **항목마다 적는 것:** `rule`(수정의 종류, 예: 띄어쓰기·호응·범용 포장), `tier`(틀린 것을 바로잡은 수정은 `확실`, 그 밖은 `권장`), `확실`이 아닌 수정에는 `reason`. 빠지면 `redpen`이 적용하지 않는다(Word 설명서 3절과 같다). 무엇을 고칠지는 SKILL.md만 따른다.
- 표시만 하는 표기 문제(실제 인용, 또는 사용자가 대사를 편집 범위에서 뺐을 때의 대사)는 보고서의 '대사 표기' 표에 모으고, 메모는 첫 자리에 하나만 단다.
- 장식이나 범용 포장을 지운 항목에 `"decor": true`를 달면 편집 보고서의 '지운 장식 표현' 구역에 모인다.
- 원고에 이미 빨간·파란 글자나 취소선·밑줄이 쓰였으면(작가 메모 등) 교정 표시 글자 모양에 옅은 음영(지움 #FFD9D9, 넣음 #D9E6FF)을 더하고 보고서에 적는다. 음영이 있는 것만 교정 표시다.
- 원고 폴더에 쓸 수 없으면(업로드 폴더 등) 결과를 현재 폴더에 쓰고 알린다.
- 표·글상자 안 문단도 고칠 수 있다. 그때는 표를 품은 바깥 문단의 줄 배치 캐시도 지워 한글이 표 높이를 다시 계산하게 한다.
- 하지 않는 것: 개체(구역 설정·표·그림) 자리를 옮기거나 지우는 편집(거부), 형광펜·제목 표시·변경 추적 표시가 있는 문단의 편집(거부), 한글 메모 달기(이유는 보고서에 적는다), 수락·거절 버튼.
- 확인 상태: 이 환경에는 한글이 없어(LibreOffice도 HWPX를 열지 못함) 자동 검증까지만 했다. 작가가 한글에서 한 번 열어 모양을 확인해야 한다.

## 작업 순서

1. `hwpx_tool.py text 원고.hwpx`로 번호 붙은 문단을 읽고 SKILL.md대로 편집한다. 대조·일관성 도구에는 원본을 그대로 넣는다(`fidelity_check.py facts`, `consistency.py check 1화.hwpx …`). 위치 번호가 편집 도구와 같다.
2. 편집 목록 JSON을 쓴다. 문단은 `find`(그 문단에만 있는 문구)로 가리키는 것을 기본으로 하고, 번호(`para`)를 쓸 때는 위 도구들이 보인 번호를 그대로 쓴다. `old`/`new`, `new_text`, `after`·`before`/`text`로 고치고, 모든 수정 항목에 `rule`·`tier`를 적는다. `확실`이 아닌 수정과 문단 다시 쓰기·삭제·합치기·나누기에는 짧은 `reason`도 적는다(보고서에 들어간다). 작가에게 물을 것은 `{"find": "…", "op": "comment", "text": "물을 내용"}`으로 적으면 보고서의 메모 줄로 들어간다.
3. `hwpx_tool.py redpen 원고.hwpx edits.json` → `_redpen.hwpx`(빨간 취소선 = 지운 글자, 파란 밑줄 = 넣은 글자, 띄어쓰기·문장부호 수정은 어절째), `_편집보고서.md`. 수정 반영본은 요청할 때만 `--clean`으로 남긴다. 자동 검증이 모두 PASS일 때만 전달한다.
4. 검수: 빨간펜 파일의 수정본 텍스트(`text 교정본_redpen.hwpx --redpen final --plain`)로 SKILL.md의 검수를 하고, 짚은 문장은 편집 목록에서 고쳐 3을 다시 한다.
5. 수락·거절 버튼은 없다. 작가에게 수정마다 채택 여부를 묻지 않는다.

결과 위치는 `-o`·`--report`로 정한다(쓸 수 없는 폴더·원고에 이미 있는 빨간 글자 처리: hwpx.md).

## 지금 되는 것

- `hwpx_tool.py text 원고.hwpx [--view accept|reject|markup] [--plain]`: 문단별 텍스트(표·글상자 안 문단 포함, 표 안 문단은 '(표)' 표시). 변경 추적이 있는 파일은 수락본(accept)·원문(reject)·표시본(markup)으로 볼 수 있다.
- `hwpx_tool.py inspect 원고.hwpx`: 패키지 구조, 구역, 문단·메모 수, 변경 추적 표시와 머리 정보의 관련 요소.
- `fidelity_check.py facts·names`와 `consistency.py check`에 `.hwpx`를 그대로 넣으면 된다. 위치는 `text` 명령과 같은 문단 번호로 나온다(빈 문단·표 안 문단 포함).
- 이름공간이 아니라 요소 이름으로 찾으므로 2011년판(hancom.co.kr)과 2021년판(owpml.org) 문서를 모두 읽는다.

## 실제 한글 파일로 확인한 것(웹소설 원고 세 회차, 맥용 한글 12.30 저장)

- 읽기: 세 파일 모두 한글이 저장한 미리보기 텍스트(`Preview/PrvText.txt`)와 글자 단위로 일치했다.
- 변경 추적 설정은 머리 정보 끝의 `<hh:trackchageConfig flags="56"/>`이다. 표준 문서의 이름(trackchangeConfig)과 달리 실제 파일은 철자가 `trackchage`다. flags 값의 뜻은 공개 자료에서 찾지 못했다.
- 맥용 한글에는 변경 내용 추적 기능이 없다는 보고가 있다(2022년 사용자 글에 인용된 한컴 답변: '미지원'). 윈도우용 한글에는 [검토] 탭의 '변경 내용 추적'이 있다(한컴 도움말). 그래서 작가가 맥에서 한글을 쓰면 한글 변경 추적 파일을 만들어도 수락·거절을 할 수 없다. 이때는 DOCX 변경 추적(맥용 Word 등)을 쓰거나, 수정본과 편집 보고서로 전달한다.

## 아직 안 되는 것: 변경 추적으로 수정 기록

공개 스키마(KS X 6101 부속서 발췌)로 확인한 것:
- 글자는 `<hp:t>` 안에 있고, 변경 추적은 같은 `<hp:t>` 안에 `insertBegin`·`insertEnd`·`deleteBegin`·`deleteEnd` 표시를 꽂는다. Word처럼 지운 글자를 따로 감싸지 않는다.
- run에 `charTcId`, p에 `paraTcId`(선택) 속성이 있고, 머리 정보(head)에 `trackchangeConfig`가 있다.

확인하지 못한 것:
- 표시 요소의 속성(작성자·시각·변경 번호를 잇는 방식)
- 머리 정보의 변경 목록과 작성자 목록 형식
- 한글이 추가로 요구하는 조건(줄 배치 캐시 등). 구조가 조금만 어긋나도 한글이 본문 일부를 버리거나, 숨긴 삭제 글자가 되살아나는 사례가 공개 이슈에 있다.

추측으로 만들지 않는다. 한글이 저장한 샘플로 구조를 확인한 뒤 구현하고, 만든 파일은 작가가 한글에서 열어 수락·거절이 되는지 확인한다.

## 샘플 만드는 법(작가에게 부탁할 때)

1. 한글에서 새 문서에 짧은 문장 서너 개를 쓰고 HWPX로 저장한다(변경 추적 전 파일).
2. 변경 내용 추적을 켠다(보통 [검토] 탭. 메뉴 이름은 판에 따라 다를 수 있다).
3. 한 곳에 글자를 넣고, 한 곳의 글자를 지우고, 한 곳의 글자를 바꾸고(지우고 넣기), 문단 하나를 나누고, 메모 하나를 단다.
4. 다른 이름으로 HWPX 저장한다(변경 추적 후 파일). 두 파일을 함께 준다.

## 진짜 변경 추적이 필요할 때

- 작가가 한글에서 '다른 이름으로 저장 → Word 문서(.docx)'로 바꿔 주면 DOCX 흐름으로 변경 추적을 남긴다(표·각주 등 서식은 변환에서 달라질 수 있다).
- 구형 .hwp(바이너리)는 읽지 않는다. HWPX나 DOCX로 저장해 달라고 한다.
